本项目作为地图服务前端代理服务器和前端缓存库使用

1. /api/proxy/wfs — WFS 远程代理

  api-server.js:309-359 中定义的代理端点是用来转发远程 WFS/GeoJSON 请求的，目的是绕过浏览器的 CORS 限制。它和本地的 SQLite 数据库、public/data
  目录下的 JSON 文件没有任何关系。

  浏览器 → /api/proxy/wfs?url=<远程WFS服务> → fetch 远程数据 → 返回给浏览器

2. /api/proxy/mapserver — MapServer REST 代理（ArcGIS / GeoScene）

  api-server.js:394-491 中定义的代理端点，用于转发 ArcGIS/GeoScene MapServer REST 请求，绕过浏览器 CORS 限制。

  与 WFS 代理的关键差异：

  ┌─────────────────────┬──────────────────────────────┬───────────────────────────────────────┐
  │        特性          │     /api/proxy/wfs (WFS)     │    /api/proxy/mapserver (MapServer)   │
  ├─────────────────────┼──────────────────────────────┼───────────────────────────────────────┤
  │ HTTP 方法            │ 仅 GET                      │ ALL（GET + POST）                     │
  ├─────────────────────┼──────────────────────────────┼───────────────────────────────────────┤
  │ 长参数支持           │ 靠 URL query string 传参     │ POST body 传参，无 URL 长度限制       │
  ├─────────────────────┼──────────────────────────────┼───────────────────────────────────────┤
  │ 请求体转发           │ 不支持                       │ 支持 application/x-www-form-urlencoded │
  ├─────────────────────┼──────────────────────────────┼───────────────────────────────────────┤
  │ 超时                 │ 30 秒                       │ 60 秒（MapServer 空间查询更慢）       │
  ├─────────────────────┼──────────────────────────────┼───────────────────────────────────────┤
  │ 大响应处理           │ 全部 JSON.parse 后包装返回   │ ≤10MB JSON 包装；>10MB 流式管道直传   │
  ├─────────────────────┼──────────────────────────────┼───────────────────────────────────────┤
  │ 分页支持             │ 无                          │ 透传 resultOffset/resultRecordCount    │
  └─────────────────────┴──────────────────────────────┴───────────────────────────────────────┘

  两种调用模式：

  ── 模式一：GET 简单查询（向后兼容）──
    GET /api/proxy/mapserver?url=<encoded_url>
    适用：参数少的普通查询

  ── 模式二：POST body 查询（推荐，规避 URL 长度限制）──
    POST /api/proxy/mapserver
    Body (JSON):
    {
      "baseUrl": "https://geo.example.com/.../MapServer/0/query",
      "params": { "where": "...", "geometry": "{...}", "outFields": "*", "f": "geojson" },
      "usePostForward": true       // true=用 POST 转发给 MapServer，false/不传=拼成 GET
    }
    适用：geometry / where 条件非常长时，避免 GET URL 超长导致失败

  大响应流式转发机制：
    响应 ≤ 10MB → JSON.parse → { success, contentType, data } 包装返回
    响应 > 10MB → 流式管道直传，响应头带 x-proxy-stream: 1
                → 不把数据全部读入内存，避免 OOM

  分页参数：
    可在 params 中传入 resultOffset / resultRecordCount 分页拉取：
    { "params": { ..., "resultOffset": 0, "resultRecordCount": 500 } }

  前端调用示例：

    // 简单查询（GET 模式）
    fetch('/api/proxy/mapserver?url=' + encodeURIComponent(
      'https://geo.example.com/.../MapServer/0/query?where=1=1&outFields=*&f=geojson'
    ));

    // 空间查询（POST 模式 —— geometry 再大也不受 URL 限制）
    fetch('/api/proxy/mapserver', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({
        baseUrl: 'https://geo.example.com/.../MapServer/0/query',
        params: {
          where: 'LONG_COMPLEX_CONDITION...',
          geometry: 'POLYGON((...几千个坐标点...))',
          geometryType: 'esriGeometryPolygon',
          spatialRel: 'esriSpatialRelIntersects',
          outFields: '*',
          f: 'geojson'
        },
        usePostForward: true
      })
    });

    // 分页拉取
    fetch('/api/proxy/mapserver', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({
        baseUrl: 'https://geo.example.com/.../MapServer/0/query',
        params: {
          where: '1=1',
          outFields: '*',
          f: 'geojson',
          resultOffset: 0,
          resultRecordCount: 500
        },
        usePostForward: true
      })
    });

3. SQLite ↔ public/data JSON 的实际交互机制

  核心在 sqlite-db-manager.js，采用的是双写 + 定时同步架构：

  路径映射

  文件路径通过 pathToTableName() / tableNameToPath() 与 SQLite 表名互转：

  public/data/gis/oblique_photography.json  ←→  SQLite 表: gis_oblique_photography

  每张表结构固定为 (id, json_data, version, created_at, updated_at)，整份 JSON 作为一个字符串存在 json_data 字段里（不是按字段拆行）。

  三条数据流

  ┌───────────────────────┬────────────────────────┬────────────────────────────────────┐
  │         操作          │        数据流向        │                说明                │
  ├───────────────────────┼────────────────────────┼────────────────────────────────────┤
  │ 读取 GET /api/data/*  │ DB 优先 → 文件系统回退 │ 先查 SQLite 表，查不到再读磁盘文件 │
  ├───────────────────────┼────────────────────────┼────────────────────────────────────┤
  │ 写入 POST /api/data/* │ 只写 DB                │ 数据写入 SQLite，不直接写磁盘      │
  ├───────────────────────┼────────────────────────┼────────────────────────────────────┤
  │ 同步 POST /api/sync   │ DB ↔ 磁盘              │ 两个方向都可手动触发               │
  └───────────────────────┴────────────────────────┴────────────────────────────────────┘

  启动时的智能同步 (smartSyncFromFilesystem)

  服务器启动时（api-server.js:100），会比较文件修改时间 mtime 和数据库 updated_at：

  遍历 public/data/**/*.json
    ├─ 数据库中不存在此表 → import（首次导入）
    ├─ 文件 mtime > 数据库 updated_at → update（文件更新覆盖DB）
    └─ 文件 mtime ≤ 数据库 updated_at → skip（已是最新）

  自动定时同步（DB → 文件）

  sqlite-db-manager.js:583-595 启动一个定时器，每 10 秒将数据库内容写回磁盘：

  setInterval → syncToFilesystem() → 逐表读取 json_data → 写入 public/data/ 对应路径

  写入前会先比较内容，内容未变则跳过（避免无意义的磁盘 IO）。

  ---
  总结：完整的数据流

                      ┌─────────────────────────┐
   前端 POST 写入     │    SQLite (configs.db)   │
   ─────────────────► │                          │
                      │  表: gis_oblique_photography
   前端 GET 读取      │      json_data: "{...}"   │
   ◄───────────────── │                          │
     (优先查DB)       └──────────┬──────────────┘
                                │
                      每10秒自动 syncToFilesystem()
                      启动时 smartSyncFromFilesystem()
                                │
                      ┌─────────▼──────────────┐
                      │  public/data/           │
                      │    gis/                  │
                      │      oblique_photography.json
                      └────────────────────────┘

  简单说：SQLite 是主存储，public/data 是同步副本。前端读写都走
  SQLite，文件系统由定时器自动同步保持一致性。启动时则反向——如果文件比数据库新，就用文件内容更新数据库。
